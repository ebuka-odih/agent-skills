# Zero-downtime migrations

During a deploy, **old code runs against the new schema** (and briefly new code against the old one). Every migration must be safe for both.

**Output:** migration(s) split by phase, each reviewed against [references/zero-downtime.md](references/zero-downtime.md), plus the deploy order in the PR description.

## Steps
1. **Classify the change** with the table in [references/zero-downtime.md](references/zero-downtime.md): safe, needs a pattern, or needs several deploys.
2. **Split into phases** — *expand* (add nullable column / new table / index concurrently) → *migrate* (dual-write in code, backfill in batches) → *contract* (switch reads, then drop the old thing in a later deploy).
3. **Write it per stack** — [references/stacks.md](references/stacks.md) (Laravel / Alembic snippets: lock timeout, concurrent index, NOT VALID constraints, batched backfill).
4. **Check** — `backend-scan.sh` flags drop/rename/type changes, NOT NULL without default, non-concurrent indexes; the hook warns as you write.
5. **Rehearse** on a copy of production-sized data; time it; test the down migration or write why there is none.

## Hard rules
- Never drop or rename a column the running code still reads; drops ship one deploy after the code stops using it.
- Big-table indexes are built concurrently; risky DDL sets `lock_timeout` (fail fast, retry) instead of queueing behind traffic.
- Backfills run in batches outside the schema migration (a job or command), resumable and idempotent.
- Autogenerated migrations are read line by line before commit.
